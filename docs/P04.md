# P04 : VALIDATE AND BUILD PHASE

P3 produced hypotheses in natural language with citations; P4's job is to independently re-derive whether each one is actually supported by the graph, and to build the symptom→cause evidence path the report will show. Its governing principle is "knowledge-as-veto" : a failed deterministic check rejects the claim outright, and nothing downstream , not the LLM critique, not the model's own confidence can talk a failure back into a pass.

## What it does

The entry point is `validate_investigation()::p4_validate.py`. It revalidates that scope/ranking/invest all match the investigation, requires an authoritative onset timestamp, then assesses each hypothesis individually , note this is now hypothesis-owned, not candidate-owned; candidate summaries are described as "compatibility views only."

For each hypothesis, `assess_hypothesis::p4_validate.py` does three things:

1. Re-resolve the evidence from the graph, trusting nothing the model said. `policy.owned_evidence()::policy.py` looks up each cited wrapper and its live source node via the OBSERVED_ON provenance edge, and independently checks: the incident id matches, the timestamp is finite and inside the window, the relationship is positive-support (polarity support, weight > 0), the source belongs to the right service, the service is in scope, and the record isn't ambiguously owned. Anything failing is dropped and crucially, "missing evidence is a gap, never manufactured refutation".
2. Runs the deterministic checks. These are the pure functions in `validators.py`:
- `level_veto` uses a topological-depth convention: level is depth over DEPENDS_ON in call direction (entry service = 0, callees deeper). Faults originate deeper and manifest upward, so a causal claim whose cause sits strictly shallower than its effect is physically implausible and rejected.
- svar_lite is the cheapened CORAL two-window falsifier: an anomaly must be present in-window (|z| ≥ 3) and a real excursion against baseline (gamma ≥ 3), with direction checked per-series rather than per-service , because a service can legitimately have latency up while a resource metric moves down.
3. Builds the evidence path. `pathfind.find_evidence_path()::pathfind.py` does a bounded BFS (≤6 hops, ≤60 nodes) from the anchor to the candidate, walking only frozen invariant scope edges , the graph-backed fallback mode is retained "only for historical viewing and never supplies causal support." Each edge then gets support assigned from policy.propagation_support(), which is strict: only admitted same-trace caller-parent/callee-child error spans qualify, with the child interval fitting inside the parent. Metrics or logs on the callee cannot prove the link. Path nodes get role labels (symptom / intermediate / candidate_cause / corroborating).

After that, two L4-style extras: chain coherence (does this candidate's supported callers-closure explain ≥2 other branches' symptoms → CC ∈ {0, 0.5, 1}) and an optional single critique call , strictly the first hypothesis, strictly only if an llm is passed, and it can only lower confidence, never raise it. If the verdict is fail, a ValidatorRefute Evidence node and a refute-polarity HAS_EVIDENCE edge are persisted.

Finally `policy.evidence_strength()::policy.py` converts the assessment into a score and rule : 0.85 cross_modal_consensus (≥2 modalities), 0.7 single_modality, 0.4 inference_only and an eligible flag requiring timing, a plausible path, and score ≥ θ=0.6. Eligible non-anchor candidates get a volatile ASSOCIATED_WITH edge to the anchor service. That eligible flag is the permission signal P5's conservative policy later reads.
