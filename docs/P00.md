# P0 : RIGGER & RESOLVE

It takes the raw input , a symptom string like "checkout latency up", an optional alert id, and an optional trigger timestamp and produces the object every later phase consumes: an Investigation carrying a resolved anchor service, a time window, a budget, and an isolated session graph with an Incident node written into it.

## What it does

The entry point is `trigger_investigation()::p0_resolve.py`, with anchor resolution split into `resolve()::p0_resolve.py`. Four things happen:

1. Anchor resolution : two paths, alert-first. If an alert_id is supplied, P0 reads the Alert's authoritative OBSERVED_ON target: a Service becomes the anchor, an Instance resolves through its service_id to the owning Service (recording via_instance), and anything else is unmatched. If no alert id is given, it falls through to text linking (linking.link_entity).

2. Entity linking from the symptom. `linking.py` reads the whole Service|Instance catalog (bounded, with payload admission that rejects oversized fields), then scores matches token-aware: exact normalized-name match = 1.0, a contained alias = 0.9, and a SequenceMatcher fuzzy ratio above a threshold (0.85 for short queries, else 0.75) for single-token aliases ≥4 chars that aren't stopwords. The important part is the ambiguity rule: if more than one service matches and either the match is exact-but-tied or the top two scores are within fuzzy_margin (0.10), pick_best returns None and P0 abstains , ambiguity is never broken by ID. If the catalog read overflows, it refuses to resolve at all rather than match against a partial catalog.

3. The onset clock, with explicit provenance. This is where P0's correctness really lives. trigger_ts resolves in strict precedence: an explicit argument → the supplied alert's timestamp → the latest Alert observed on the anchor service → otherwise MissingOnsetError. The Investigation records time_source (explicit_trigger / supplied_alert / service_alert) and, when both an alert and an override exist, a clock_provenance dict with alert_ts and override_delta_ms. Timestamps are normalized to epoch-ms by to_epoch_ms. The window is then [trigger_ts − 15min, trigger_ts + 15min] (WINDOW_PAD_MS).

4. Session creation and writes. `session_graph()::client.py` deletes any stale graph at the name and does a GRAPH.COPY from incidentgraph:demo into incidentgraph:session:{id} , so this is where tenant isolation begins, and investigation writes never touch the read-only demo graph. P0 then MERGEs the Incident node (status='investigating', verdict='open', symptom, onset, anchor, time source, clock provenance) and the AFFECTS edge to the anchor.

The output is the Investigation contract, which also carries the budget created here, BudgetMeter(...).as_dict(), seeded from the default InvestigationBudget , because P0 is where the meter's lifecycle starts.
